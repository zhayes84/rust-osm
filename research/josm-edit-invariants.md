# Editing invariants and dependencies for a building-edit prototype

Research date: 2026-10-16. Resolves the factual investigation in [Identify editing invariants and data dependencies a prototype must preserve](https://github.com/zhayes84/rust-osm/issues/3).

Reference: JOSM/JOSM commit `d663b2a601ba0f94376f48ee216a16f4a60a493a`. All source links below pin that revision. Selected Java sources and tests were downloaded and read; tests were **not executed**, and no performance measurements were taken. This is a bounded source investigation, not an exhaustive compatibility specification.

The user reports lag moving nodes of existing building outlines, including alignment corrections and extensions. Their dataset, JOSM version, plugins, styles, projection, and hardware are not yet known. The conclusions below describe the pinned reference, not a diagnosis of that session.

## Result

A useful editor prototype must preserve object identity, shared topology, edit state, and reversible changes while keeping derived spatial and visual state coherent. It cannot establish editing performance by moving independent display vertices alone. The source exposes both local work (moved nodes, incident ways, parent relations) and wider work (listeners, searches, rendering); total dataset size alone is not a sufficient workload description. These are implications of the traced mechanisms below, not a choice of Rust representation.

One compatibility assumption needs explicit review: JOSM can continue the preceding move command across separate drags of the same affected nodes. Exactly one undo entry per mouse gesture is therefore **not** a reliable description of its current behavior. [SelectAction, command continuation](https://github.com/JOSM/josm/blob/d663b2a601ba0f94376f48ee216a16f4a60a493a/src/org/openstreetmap/josm/actions/mapmode/SelectAction.java#L841-L870)

## Source facts

### Identity, topology, and the affected set

- A way is an ordered array of node references. Closure uses the same first and last node object, not merely coincident coordinates; an area additionally needs at least three distinct nodes. Moving that shared endpoint must preserve closure. `setNodes` removes old reverse references, installs the new list, adds reverse references, clears relevant style caches, and emits a nodes-changed event. [Way](https://github.com/JOSM/josm/blob/d663b2a601ba0f94376f48ee216a16f4a60a493a/src/org/openstreetmap/josm/data/osm/Way.java#L33-L72), [closure and area](https://github.com/JOSM/josm/blob/d663b2a601ba0f94376f48ee216a16f4a60a493a/src/org/openstreetmap/josm/data/osm/Way.java#L483-L507)
- `MoveCommand` expands selected primitives through `AllNodesVisitor`, which uses a set. A node selected directly and also through a way moves once; an incomplete way is skipped. Select-mode dragging initially takes selected nodes and ways, not selected relations. This does not prevent a moved node from changing geometry used by unselected ways or relations. [AllNodesVisitor](https://github.com/JOSM/josm/blob/d663b2a601ba0f94376f48ee216a16f4a60a493a/src/org/openstreetmap/josm/data/osm/visitor/AllNodesVisitor.java), [SelectAction](https://github.com/JOSM/josm/blob/d663b2a601ba0f94376f48ee216a16f4a60a493a/src/org/openstreetmap/josm/actions/mapmode/SelectAction.java#L714-L732)
- Relations keep ordered member records and reverse references. A coordinate-only move does not replace relation membership, member roles, way IDs, or way node order. Geometry/bounds can change while those records remain unchanged. Relation bounding-box traversal has a visited set to handle repeated/cyclic references; that is not evidence that every relation operation is cycle-safe. [Relation members](https://github.com/JOSM/josm/blob/d663b2a601ba0f94376f48ee216a16f4a60a493a/src/org/openstreetmap/josm/data/osm/Relation.java#L31-L65), [bounds](https://github.com/JOSM/josm/blob/d663b2a601ba0f94376f48ee216a16f4a60a493a/src/org/openstreetmap/josm/data/osm/Relation.java#L445-L475)
- A way installed in a dataset checks that its nodes belong to that dataset and are not deleted. Complete visible nodes must have known coordinates. Adding a node directly to an incomplete way is rejected. These are stronger constraints than drawing a plausible polygon. [Way checks](https://github.com/JOSM/josm/blob/d663b2a601ba0f94376f48ee216a16f4a60a493a/src/org/openstreetmap/josm/data/osm/Way.java#L405-L462), [dataset integrity](https://github.com/JOSM/josm/blob/d663b2a601ba0f94376f48ee216a16f4a60a493a/src/org/openstreetmap/josm/data/osm/Way.java#L545-L579)

### Moving, inserting, undoing, and cancelling

- A move records each node's previous geographic coordinate, projected coordinate, and modified flag. Initial execution changes coordinates and marks movable nodes modified. Continuing the drag applies displacement from saved coordinates; undo restores the previous geographic coordinates and modified flags. Thus undo of an already-dirty node must retain its earlier dirty status. [MoveCommand](https://github.com/JOSM/josm/blob/d663b2a601ba0f94376f48ee216a16f4a60a493a/src/org/openstreetmap/josm/command/MoveCommand.java#L192-L310), [OldNodeState](https://github.com/JOSM/josm/blob/d663b2a601ba0f94376f48ee216a16f4a60a493a/src/org/openstreetmap/josm/command/Command.java#L65-L130)
- SelectAction reuses a suitable last move command, including the final command within a sequence, if its dataset and affected-node set match. A new mouse press can change that command's base point. The undo grouping contract needs observation and a human compatibility decision; command-level tests alone do not establish gesture boundaries. [SelectAction](https://github.com/JOSM/josm/blob/d663b2a601ba0f94376f48ee216a16f4a60a493a/src/org/openstreetmap/josm/actions/mapmode/SelectAction.java#L733-L787), [continuation](https://github.com/JOSM/josm/blob/d663b2a601ba0f94376f48ee216a16f4a60a493a/src/org/openstreetmap/josm/actions/mapmode/SelectAction.java#L841-L870)
- Dragging a virtual midpoint creates a sequence: add one real node, change the node list of each chosen way segment, then move the new node. The new node becomes selected. Coincident midpoint locations alone do not justify connecting otherwise unrelated segments; selection affects which eligible overlapping segments are included. This is a concrete candidate for the user's building-extension workflow, but the user's actual insertion technique is unconfirmed. [VirtualManager](https://github.com/JOSM/josm/blob/d663b2a601ba0f94376f48ee216a16f4a60a493a/src/org/openstreetmap/josm/actions/mapmode/SelectAction.java#L1284-L1355)
- Changing a way's node list marks the way modified and uses the generic command snapshot for undo. Adding a node adds it to the dataset and marks it modified; undo removes it. Sequence undo runs subcommands in reverse order. A subcommand returning false can roll back preceding subcommands; exceptions take a separate reported-exception path, so do not assume general transaction rollback from this implementation. [AbstractNodesCommand](https://github.com/JOSM/josm/blob/d663b2a601ba0f94376f48ee216a16f4a60a493a/src/org/openstreetmap/josm/command/AbstractNodesCommand.java), [AddCommand](https://github.com/JOSM/josm/blob/d663b2a601ba0f94376f48ee216a16f4a60a493a/src/org/openstreetmap/josm/command/AddCommand.java#L52-L69), [Command snapshots](https://github.com/JOSM/josm/blob/d663b2a601ba0f94376f48ee216a16f4a60a493a/src/org/openstreetmap/josm/command/Command.java#L150-L183), [SequenceCommand](https://github.com/JOSM/josm/blob/d663b2a601ba0f94376f48ee216a16f4a60a493a/src/org/openstreetmap/josm/command/SequenceCommand.java#L109-L179)
- A move outside the world restores a displacement checkpoint. On release, warnings can cover attached filtered-out ways, large distance, or many elements; rejecting a warning calls undo. These mechanisms differ: checkpoint restoration is not a full command undo. This investigation did not establish a general Escape-to-cancel contract. [World limit](https://github.com/JOSM/josm/blob/d663b2a601ba0f94376f48ee216a16f4a60a493a/src/org/openstreetmap/josm/actions/mapmode/SelectAction.java#L768-L785), [confirmation and undo](https://github.com/JOSM/josm/blob/d663b2a601ba0f94376f48ee216a16f4a60a493a/src/org/openstreetmap/josm/actions/mapmode/SelectAction.java#L880-L968)

### Coordinates, incomplete data, and persistence

- Nodes store geographic doubles and cached projected doubles with a projection cache key. Setting geographic coordinates invalidates the projection cache; setting projected coordinates converts through the current projection and retains the projected cache. A null coordinate can make a visible node incomplete. The display/projection coordinate and authoritative geographic coordinate therefore cannot be silently conflated. [Node coordinate handling](https://github.com/JOSM/josm/blob/d663b2a601ba0f94376f48ee216a16f4a60a493a/src/org/openstreetmap/josm/data/osm/Node.java#L28-L131)
- Incomplete means identity/type are known but full data is absent. Download-area membership is separate: a complete node can be outside the downloaded area. `isOutsideDownloadArea` exempts new/undeleted nodes, absent datasets, and datasets with no area; otherwise it tests geographic membership. Do not collapse incomplete, out-of-view, and outside-download-area into one state. [AbstractPrimitive flags](https://github.com/JOSM/josm/blob/d663b2a601ba0f94376f48ee216a16f4a60a493a/src/org/openstreetmap/josm/data/osm/AbstractPrimitive.java#L31-L81), [Node download area](https://github.com/JOSM/josm/blob/d663b2a601ba0f94376f48ee216a16f4a60a493a/src/org/openstreetmap/josm/data/osm/Node.java#L349-L358)
- A coordinate-only move marks nodes modified; reindexing dependent ways/relations does not itself mark their persisted content modified. Inserting a node changes the way's ordered references and therefore its modified state. The API dataset classifies additions, updates, and deletions from identity/newness/modified/deleted/visible state. XML writing records edit action and version and skips incomplete primitives. A screenshot is insufficient to verify these semantics. [MoveCommand](https://github.com/JOSM/josm/blob/d663b2a601ba0f94376f48ee216a16f4a60a493a/src/org/openstreetmap/josm/command/MoveCommand.java#L278-L310), [APIDataSet](https://github.com/JOSM/josm/blob/d663b2a601ba0f94376f48ee216a16f4a60a493a/src/org/openstreetmap/josm/data/APIDataSet.java#L40-L115), [OsmWriter](https://github.com/JOSM/josm/blob/d663b2a601ba0f94376f48ee216a16f4a60a493a/src/org/openstreetmap/josm/io/OsmWriter.java#L241-L288), [metadata](https://github.com/JOSM/josm/blob/d663b2a601ba0f94376f48ee216a16f4a60a493a/src/org/openstreetmap/josm/io/OsmWriter.java#L344-L389)

### Propagation, concurrency, and memory

The observed move path is:

```text
MoveCommand -> Node.setEastNorth -> DataSet.fireNodeMoved
  -> remove node from spatial index -> change coordinate -> reinsert node
  -> visit referring ways/relations
     -> remove/recompute/reinsert way; clear way style cache
     -> if bounds changed, update referring relations recursively
  -> queue NodeMovedEvent -> dispatch on endUpdate
```

`QuadBucketPrimitiveStore` uses quad buckets for nodes and ways, an array list for relations, and a bounding-box filter over relations for relation searches. It updates each node's referrers; parent-relation propagation after way/relation updates is conditional on a changed bounding box. This is **reference fan-out**, not proof that every node move scans the whole dataset. [QuadBucketPrimitiveStore](https://github.com/JOSM/josm/blob/d663b2a601ba0f94376f48ee216a16f4a60a493a/src/org/openstreetmap/josm/data/osm/QuadBucketPrimitiveStore.java), [Way.updatePosition](https://github.com/JOSM/josm/blob/d663b2a601ba0f94376f48ee216a16f4a60a493a/src/org/openstreetmap/josm/data/osm/Way.java#L584-L608)

`DataSet.beginUpdate` takes a write lock; `endUpdate` batches or coalesces events, releases the write lock, and dispatches with a read lock held. `fireNodeMoved` queues a node event after reindexing; it does not emit a separate way-nodes-changed event for every incident way. Listeners can do further work, so this trace does not measure the complete drag cost or demonstrate safe concurrent rendering by itself. [DataSet update/event handling](https://github.com/JOSM/josm/blob/d663b2a601ba0f94376f48ee216a16f4a60a493a/src/org/openstreetmap/josm/data/osm/DataSet.java#L990-L1148)

Memory accounting must include more than coordinates: identity lookup storage; spatial indexes; way reference arrays; relation member arrays; reverse references; primitive metadata/tags; projected coordinates and style caches; selections; and retained command snapshots. JOSM already makes targeted memory choices, including inline coordinate doubles, packed flags, tag string arrays, and reverse references represented as null/single reference/array. Some way-clone constructors explicitly warn about retained reverse references. These are storage facts, not evidence that Rust automatically saves a particular percentage or that a specific alternative layout wins. [DataSet fields](https://github.com/JOSM/josm/blob/d663b2a601ba0f94376f48ee216a16f4a60a493a/src/org/openstreetmap/josm/data/osm/DataSet.java#L125-L170), [primitive styles and referrers](https://github.com/JOSM/josm/blob/d663b2a601ba0f94376f48ee216a16f4a60a493a/src/org/openstreetmap/josm/data/osm/OsmPrimitive.java#L148-L173), [reverse-reference storage](https://github.com/JOSM/josm/blob/d663b2a601ba0f94376f48ee216a16f4a60a493a/src/org/openstreetmap/josm/data/osm/OsmPrimitive.java#L591-L665), [metadata and tags](https://github.com/JOSM/josm/blob/d663b2a601ba0f94376f48ee216a16f4a60a493a/src/org/openstreetmap/josm/data/osm/AbstractPrimitive.java), [clone warning](https://github.com/JOSM/josm/blob/d663b2a601ba0f94376f48ee216a16f4a60a493a/src/org/openstreetmap/josm/data/osm/Way.java#L199-L233)

## Implications, hypotheses, and open decisions

**Recommended correctness floor:** preserve identity, topology, untouched metadata, coherent derived geometry, accurate modified/new/deleted state, and undo restoration for every supported edit. A prototype may explicitly exclude an input category or operation; it should not appear to support it while silently changing its semantics. This is an engineering recommendation inferred from the facts above.

**Compatibility choices for the human:** exact undo continuation across repeated drags; virtual-node/shared-segment behavior; modifier-driven merging; filtering warnings and thresholds; supported projections; whether first-prototype input must include multipolygon buildings and incomplete data. Familiar workflows suggest testing these intentionally, but no choice is made here.

**Hypotheses to measure:** local edit cost may depend on incident-way length, shared-node fan-out, relation fan-out/depth, and event subscribers, independently of total dataset count. Memory may depend materially on reference density, style cache occupancy, and undo history. GPU rendering alone cannot remove the traced data updates, but this investigation does not rank them against paint cost or prove any is the user's bottleneck.

Useful next questions are therefore sharp: (1) Which insertion/drag/undo sequence reproduces the user's lag? (2) Which topology and projection cases must the first prototype support or explicitly reject? (3) Does a measured trace show time in reindexing/referrer propagation, listeners, or rendering, and how does that change when local fan-out is held constant while the surrounding dataset grows? These questions can be answered before selecting storage, threading, or rendering frameworks.

No Rust representation, UI toolkit, renderer, persistence mechanism, or implementation schedule is selected by this note. Broad plugin behavior, all DrawAction modes, complete selection history restoration, global cancellation behavior, and real upload/conflict handling remain outside this bounded investigation.
