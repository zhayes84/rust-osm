# JOSM existing-node drag path and measurement boundaries

Research for [issue #2](https://github.com/zhayes84/rust-osm/issues/2), 2026-10-16. Source baseline: JOSM Git mirror commit `d663b2a601ba0f94376f48ee216a16f4a60a493a`. All source links below are pinned to that commit. This is static source research, not a profile, diagnosis, or replacement architecture decision. No application or performance tests were run.

The reported symptom is lag while dragging existing building-outline nodes. The user's JOSM build, dataset, styles, plugins, renderer, hardware and display configuration are unknown. The trace covers ordinary select-mode movement of an existing node; virtual-node creation, rotation, scaling and merging introduce additional paths. A selected way or multiple selected objects changes how many nodes are moved.

## Findings

The normal drag path mutates the editable graph and updates dependent state before requesting a repaint. The default styled renderer then prepares styles in parallel, waits for those tasks, sorts, and draws while holding a dataset read lock. A GPU replacement could help drawing, but source inspection cannot establish that drawing dominates the reported delay. The pinned version also contains a selectable tiled renderer with a different scheduling path. [Drag command update][select-update], [renderer][render], [renderer selection][factory], [tiled path][tiled].

There is an intentional initiation gate worth distinguishing from continuing lag. On mode entry JOSM reads `edit.initial-move-delay`, default **200 ms**, and `edit.initial-move-threshold`, default **5 pixels**. The press handler records `mouseDownTime = System.currentTimeMillis()` before hit testing. MOVE drag events return while elapsed time since that handler timestamp is below the configured delay, then must exceed the movement threshold. It is not timed from mode entry or `MouseEvent.getWhen()`. Preferences can override both values. An adjacent comment says 100 milliseconds, but the loaded default is 200. These checks explain a possible initial hesitation, not persistent lag after movement has started. [Preferences][select-prefs], [press handler][select-press], [drag gates][select-drag].

## Instrumentable call chain

1. **Press, hit testing and selection.** `SelectAction.enterMode` installs mouse listeners. `mousePressed` records the press, converts screen position to projected coordinates, calls `getNearestNodeOrWay`, determines the mode, and updates selection. These costs precede the first accepted movement. Ordinary Swing delivery is expected on the event-dispatch thread (EDT); instrumentation should record actual thread identity rather than assume it for synthetic tests or plugin calls. [Mode setup][select-prefs], [press][select-press].
2. **Accepted drag.** `mouseDragged` checks layer visibility, modifier/mode state, the initiation gates and duplicate coordinates. Merge mode can additionally search for a nearby node. It converts the current pointer position and calls `updateCommandWhileDragging`, followed by `mv.repaint()`. [Drag][select-drag].
3. **Command update under write lock.** The handler obtains selected nodes/ways, expands them to affected nodes, and enters `DataSet.update`. If the last command is a `MoveCommand` for the same affected nodes, it saves a checkpoint and applies a new absolute displacement from the original node state; otherwise it creates and executes a command through `UndoRedoHandler.add`. World-bound checks may restore the checkpoint. Thus an accepted pointer sample does not necessarily allocate a new undo command. Command-queue notifications on initial creation differ from subsequent command reuse. [Drag command][select-update], [coordinates/undo][move], [undo queue][undo], [dataset lock][dataset-update].
4. **Coordinate, spatial and style maintenance.** `MoveCommand.updateCoordinates` calls `Node.setEastNorth`; `Node.updateCoor` reaches `DataSet.fireNodeMoved`. That invokes `QuadBucketPrimitiveStore.reindexNode`, replacing the node in its spatial index and visiting its referrers. Referring ways are removed/reinserted around `Way.updatePosition`, which recomputes their bounding box and clears their cached style. Way-to-relation propagation occurs when the way bounding box changes; relation ancestors propagate when their bounding boxes change. A node directly referenced by a relation also enters relation reindexing. This is actual work on the ordinary move path, not merely a potential API operation. Projection conversion also occurs in `Node.setCoorInternal`. [Move][move], [node][node], [node event][dataset-node], [reindexing][store], [way position][way], [relation position][relation].
5. **Notifications and dependent geometry.** `DataSet.endUpdate` copies queued events at the outermost update, downgrades from write lock to read lock for dispatch, and either sends individual events or consolidated data-change events according to event counts. Direct dataset listeners execute synchronously in that dispatch. `OsmDataLayer` registers both its adapter and `MultipolygonCache`. The layer callback resets tile state, invalidates the layer, and updates save/upload flags. Multipolygon handling follows node referrers and updates cached combined polygon data on node moves; this is a separate path from bbox propagation. Other consumers registered through `DatasetEventManager` can receive immediate or queued/consolidated EDT delivery. [Batching/dispatch][dataset-update], [layer listeners][layer-listeners], [layer callback][layer-events], [multipolygon updates][multipolygon], [event manager][events].
6. **Repaint request and layer composition.** The map-view invalidation listener records invalidated layers in a set and requests repaint. `MapView.paint` calls `drawMapContent`, which can reuse a buffer for unchanged layers subject to view, clip, layer-order and preference conditions. It paints changed layers and temporary overlays into an offscreen buffer, then copies that buffer to the supplied graphics. Imagery beneath an edited data layer may therefore be reused; it is incorrect to assume imagery is fully fetched or repainted on every node movement. Imagery loading internals were not traced here. [Invalidation][invalidate], [layer composition][map-paint].
7. **Default styled renderer.** `OsmDataLayer.paintData` creates the active renderer and calls `render`. `StyledMapRenderer.render` acquires a dataset read lock with a one-second timed attempt; settings and lock acquisition precede its existing benchmark start. Inside the lock it queries visible nodes, ways and relations, computes relation styles first and then node/way styles through a fork-join pool (or sequential fallback), parallel-sorts style records, paints records, and draws virtual nodes. The caller waits for style tasks and holds the read lock through drawing. Style preparation is not all single-threaded, and moving one node does not restrict this render pass to that node's geometry. It queries the viewport, with style caches potentially avoiding recomputation. Geometry/path creation and drawing are intermixed in methods such as `drawArea`/`drawWay`; time the suboperations to isolate tessellation/path construction from Java2D calls. [Layer renderer][layer-render], [render pass][render], [style cache][styles], [drawing methods][draw].
8. **Alternative renderer and final presentation.** `StyledTiledMapRenderer` can reuse tile images, schedule a bounded group of dirty tiles on `MainApplication.worker`, cancel pending tile work, and display existing tile images while work is pending. Without a cache it falls back to the default renderer. The layer enables this cache branch only under its renderer/zoom conditions. Record the active class and branch; do not combine timings from these paths. Completion of `MapView.paint` or `g.drawImage` is a software boundary, not evidence that the new node position has reached the physical display. [Factory][factory], [tile scheduling][tiled], [layer branch][layer-render], [buffer copy][map-paint].

## Measurements this trace supports

Use one monotonic clock for durations and a gesture/sample identifier plus dataset-update and paint identifiers. Relate each painted state to the newest accepted sample it includes. Do not assume one mouse event, one command, one repaint and one visible frame correspond one-to-one. The source proves command reuse, dataset event batching, invalidated-layer set accumulation and explicit tile repaint batching; platform mouse/repaint coalescing must be observed in the actual JDK/OS configuration.

| Boundary | Record | Question separated |
| --- | --- | --- |
| Input receipt and `mousePressed`/`mouseDragged` entry | Input timestamp where available, handler entry/exit, thread, skipped-event reason, configured gates | Initial threshold versus event backlog versus handler cost |
| `DataSet.beginUpdate` | Before/after lock acquisition; outer update duration | Write-lock wait versus mutation |
| `MoveCommand` and reindexing | First/reused command; nodes, way lengths, referrer counts, changed bboxes; coordinate and index spans | Selection size, graph fanout, projection and spatial maintenance |
| `DataSet.endUpdate` | Event counts, dispatch spans per listener class; separately trace deferred listeners | Mutation versus synchronous/deferred observer work |
| Layer invalidation and `MapView.paint` | Request time, paint start/end, dirty layers, buffer reuse, newest included sample | Repaint scheduling delay versus actual paint time |
| `StyledMapRenderer.render` | Settings, read-lock wait, viewport queries, style tasks/cache misses, sort, record painting | Lock contention, preparation and drawing |
| Geometry and style elements | Path construction, multipolygon updates, text/icons, per-feature counts | Geometry/label work versus graphics submission |
| Tiled path, if active | Tile generation/state IDs, queue/cancel/start/finish, stale-image age | Responsive UI with stale geometry versus fresh rendering |
| Presentation | Platform presentation timing or externally recorded pointer and geometry | Software completion versus visible latency |

Prefer buffered trace records to synchronous per-event logging. Report distributions and worst stalls, not only mean FPS: press-to-first-update, accepted-sample-to-painted-state latency, frame intervals, handler duration, lock waits, and stale-state age. Preserve the intentional initiation delay as a separately reported component. Pair traces with CPU/allocation/GC and thread scheduling observations; all are proposed measurements, not measured results.

## Existing tools and pitfalls

`RenderBenchmarkCollector` exposes start, sort-start, draw-start and done hooks. `mappaint.render.benchmark=true` or trace logging selects its logger. Its generation interval includes viewport queries and style-list preparation; lock acquisition and preceding work are outside it. More subtly, `CapturingBenchmark.getDrawTime()` subtracts `timeGenerateDone`, **including sorting**, not `timeSortingDone`. The logger's two phases similarly overlap sorting, while its separately calculated total does not. `MapRendererPerformanceTest` sums generate + sort + draw, so its total counts sort twice at this revision. These follow directly from the timestamp expressions; use non-overlapping custom spans or correct interpretation before comparing results. [Collector][benchmark], [performance harness][performance].

The performance harness already supports warmup iterations, style-cache clearing and median outputs, and renders to an image. `AbstractMapRendererPerformanceTestParent` covers city, restriction and multipolygon datasets. These are useful rendering microbenchmark entry points, not complete pointer-to-display workloads. `SelectActionTest` includes a simulated mouse regression test that sets the initial delay to zero; `MoveCommandTest` checks coordinate updates, checkpoints and undo. Reuse behavioral examples only after deciding the desired parity contract. Tests were inspected, not executed. [Harness][performance], [renderer fixtures][fixtures], [select test][select-test], [move tests][move-test].

## What remains unknown

No bottleneck is identified. Candidate explanations supported by reachable code include intentional initial gating, long handlers/listeners, graph fanout, lock contention, viewport style/geometry work, drawing/composition, and stale rendered data tiles. Plugin callbacks can participate via dataset/command listeners and added renderers/layers; no installed plugin or plugin-specific call path was inspected. Neither GPU absence nor a JVM limitation has been established.

Before interpreting a baseline, obtain: exact JOSM build/JDK/OS, active renderer, styles and plugins, projection, viewport size/scaling/refresh rate, hardware, dataset counts and checksum, the dragged node/way IDs and relation memberships, selection/filter state, imagery layers/cache state, and whether lag is initial-only or continues throughout the gesture. A reproducible local file and recorded gesture should isolate stationary-map node dragging from panning, merging and virtual-node creation. Building tag presence alone does not characterize graph complexity or style cost.

The next decision-relevant questions are: Does the user's lag persist after the first accepted movement? Is it reproducible with a small ordinary building and with the default renderer/styles/plugins disabled? Which measured interval grows with dataset size, viewport density or relation fanout? Can a prototype preserve dependent geometry, undo and visible style correctness while improving that interval? These questions leave storage, UI toolkit and GPU strategy open.
